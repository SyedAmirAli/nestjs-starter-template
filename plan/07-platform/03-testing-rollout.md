# 07.3 · Testing and rollout

## The test that matters most

**Reward parity between client and server.**

`mobile-app/src/game/rewards.ts` and `src/modules/game/rewards/` implement the same rules
twice, in two languages of the same language, in two repositories. They *will* drift. When
they do, every player sees a success screen animate to one number and then snap to another,
and nobody will be able to say which was right.

So: a generated matrix, asserted on both sides.

```
modes    × chapters × elapsed seconds
{w, s}   × 1..10    × [1,2,3,5,8,13,15,16,25,26,30,45,60,61,70,90,91,120,200,600]
```

For every cell, assert `computeStars`, `speedMultiplier`, `baseScore`, `computeScore`,
`scoreGain` and `milestoneProgress` agree exactly. The fixture is generated once by the
server, committed as JSON to **both** repos, and run as a unit test in each. A CI failure in
the mobile repo when the server changes a constant is the entire point.

`plan/fixtures/reward-parity.json` is generated by `scripts/generate-parity-fixture.ts`.

## Test layers

### Unit — `yarn test`

Pure logic, no database:

- `rewards/` — the parity matrix, plus boundary cases at every threshold (exactly 15s,
  exactly 15.001s, 0s, negative, `NaN`).
- `levelFromXp` — level 1, a level boundary exactly, the cap at 1500.
- `contributionOf(run, questDefinition)` — every `QuestType` × every filter combination.
- `toLocalDate(instant, tz)` — DST forward and back, UTC+14, UTC−11, `Asia/Kathmandu`
  (+05:45), an invalid timezone string falling back to UTC.
- Merge rules — each quantity, asserted idempotent under repeat application.
- `RunValidator` — each rule at its boundary.

### Integration — Prisma against a real Postgres

Transaction-level correctness, which no mock can check:

- Run submission end-to-end: idempotency, milestone settlement, ledger consistency.
- Concurrent purchase with insufficient points for both — exactly one succeeds.
- Concurrent run submissions for the same level from two devices.
- Guest merge with overlapping level sets.
- A `SELECT … FOR UPDATE` deadlock does not occur under a mixed run/purchase load.

Use a disposable database per run (`glowquest_backend_test`), migrated with
`prisma migrate deploy`. Never point these at a database anyone cares about.

### E2E — `yarn test:e2e`, against a live server

Per [00-foundation/02](../00-foundation/02-inherited-modules.md), this is HTTP against a
running process — Better Auth is ESM-only and there is no in-process fixture. That
constraint is a gift here: these tests exercise the real middleware chain, the real Better
Auth router, and the real envelope.

The scenarios that must exist:

| # | Scenario                                                                                  |
| - | ----------------------------------------------------------------------------------------- |
| 1 | Anonymous sign-in → play 8 levels → correct stars, score, XP, points, 3 Powers at level 7. |
| 2 | Scenario 1 → sign in with email OTP → merge completes → nothing lost, nothing duplicated.  |
| 3 | Run the merge again → byte-identical state.                                                |
| 4 | 30 runs queued offline → one sync batch → same state as submitting them live.               |
| 5 | Re-send that batch verbatim → `accepted: 0, duplicates: 30`, no state change.               |
| 6 | Purchase with the same `Idempotency-Key` twice → one `Purchase`, identical response.        |
| 7 | Full level-pack sync from scratch → publish an edit → delta carries exactly what changed.   |
| 8 | Retire a level → the tombstone reaches a client at an older revision.                       |
| 9 | Play across a local midnight in `Asia/Dhaka` → streak increments once, not twice.            |
| 10| Miss a day with a freeze in hand → streak preserved, exactly one freeze consumed.            |
| 11| Quest completes → claim → claim again → paid once.                                          |
| 12| Anonymous player reads a leaderboard → gets rows plus `you.eligible: false, reason: ANONYMOUS`. |
| 13| Implausible run (`elapsedMs: 100`) → 422, no state change anywhere.                          |
| 14| Every endpoint without a session → 401 in the standard envelope, never HTML.                 |

Scenarios 3, 5, 6 and 11 are the idempotency suite. They are the ones that stop a flaky
connection from costing a player their progress or their points, and they should run on
every commit.

### Load

Before opening the network to real traffic:

- 1,000 runs/sec sustained against `POST /v1/runs`.
- 10,000 concurrent leaderboard reads with a one-million-entry sorted set.
- A sync batch of 100 runs from 500 devices simultaneously.

Watch for: Postgres connection exhaustion (Better Auth holds a **second** pool — see the
docblock in `src/auth/auth.ts`), lock contention on the wallet row, and Redis memory growth
from weekly leaderboard keys.

## Rollout

The app already works. Nothing here may make it work less well, so every step is reversible
and the network is introduced behind a switch.

### Stage 0 — foundation, invisible

Phase 00 ships alone: domain realignment, dead code removed, queues replaced. No client
change. Verifiable by `yarn build && yarn lint && yarn test` and a green deploy.

### Stage 1 — read-only, shadow

Ship phases 01–02 (identity, level pack). The app signs in anonymously and syncs the level
pack **but keeps playing off local SQLite**. If the sync fails, nothing observable happens.

This validates auth, anonymous accounts and content sync under real traffic before a single
reward depends on the server.

### Stage 2 — write, optimistic

Ship phase 03. Runs submit to the server; the client still renders from its own local
computation and still writes its own SQLite. The server's answer is fetched and **logged,
not applied**.

For one release, the prediction-mismatch metric is the only thing being watched. This is
the stage that catches rule drift before any player sees it.

### Stage 3 — server-authoritative

Flip the client to apply the server's rewards. Phases 04–06 (economy, retention,
leaderboards) light up. Local SQLite becomes the offline queue and cache it was always
described as.

Behind a remote-config flag, per platform, ramped 5% → 25% → 100%. The flag's off position
must be genuinely tested, not merely present — it is the rollback.

### Stage 4 — leaderboards public

Country boards first, then global. Weekly before all-time (a wrong all-time board is
embarrassing for longer). Watch the flag rate for a week before promoting anything.

## Rollback

| Stage | Rollback                                                                     |
| ----- | ---------------------------------------------------------------------------- |
| 0     | Revert the deploy. No data change.                                           |
| 1     | Remote-config off. The client falls back to the bundled pack.                |
| 2     | Remote-config off. Runs stop submitting; the local queue drains later.       |
| 3     | Flip authority back to the client. **Server data is retained**, so re-enabling does not lose the intervening runs. |
| 4     | Hide the leaderboard tab. Data keeps accruing.                               |

No rollback deletes server data. Every stage is reversible without a migration.

## Definition of done

- The parity fixture is committed to both repos and enforced in both CI pipelines.
- All 14 e2e scenarios pass against a live server.
- Load targets met with headroom.
- Every stage's off-switch has been exercised in staging, not just implemented.
